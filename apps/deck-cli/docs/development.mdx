# Developing Locally

There are two ways to work with johto depending on your goal.

## Quick start: one-command local install

From the monorepo root:

```bash
bun run local:setup
```

This builds the Rust MCP server, compiles the CLI for your platform, writes
`~/.config/johto/config.toml`, symlinks `johto` into `~/.local/bin`, and then verifies the
install — a keyless `--dry-run`, a `--stats` run, and one real agent turn.

The end-to-end turn runs against the **configured default provider** (currently OpenAI,
`gpt-5.6-terra`) with no `--provider` flag, so it exercises the real resolution path — including
falling back to Anthropic if OpenAI is unavailable. It reports which provider actually served the
turn.

This costs a small amount of real API credit per run. It is deliberate: a local model cannot
catch provider API contract breaks. The OpenAI path was silently broken for a while
(`gpt-5.6-terra` rejects function tools on `/v1/chat/completions` when reasoning is active) and no
amount of local-model testing would have surfaced it.

The gate skips only when neither `OPENAI_API_KEY` nor `ANTHROPIC_API_KEY` is set. Use
`--skip-e2e` to skip just that step.

The symlink points at the in-repo build output, so after editing CLI source you only need:

```bash
bun apps/deck-cli/build/compile.ts linux-arm64   # or your platform suffix
```

and `johto` picks it up immediately — no reinstall.

| Command | Effect |
|---|---|
| `bun run local:setup` | Install pointing at in-repo build output (default) |
| `bun run local:setup:standalone` | Copy binaries + database into `~/.local/share/johto`, the layout a `curl \| sh` user gets |
| `bun run local:uninstall` | Remove the symlink, config, and standalone tree; leaves the repo untouched |

Add `--force` to overwrite an existing `config.toml` (required when switching between the two
modes, since their paths differ), or `--skip-e2e` to skip the live agent turn.

The bootstrap **never rebuilds the card database** — it only verifies that
`database/pokemon-data.sqlite3.db` exists and is populated. To rebuild it:

```bash
bun dist-packages/card-data/scripts/rebuild.ts \
  --source packages/@pokemon-data/data \
  --out database/pokemon-data.sqlite3.db
```

Note that `rebuild.ts` reads `packages/@pokemon-data/data`, which stores one `<set>.d/` directory
per set plus a `sets.json`. The `forks/pokemon-tcg-data` submodule is raw upstream data in a
different shape (`cards/en/*.json`, `sets/en.json`) and is **not** a valid `--source`.

## In-monorepo development (recommended for contributors)

The canonical source lives in `apps/deck-cli/` (CLI) and `apps/mcp-server/` (Rust MCP server). All development happens here. The `dist-packages/` tree is CI output — do not edit it by hand.

```bash
# From the monorepo root

# Build the MCP server (one-time, ~30s)
cargo build --release --manifest-path apps/mcp-server/Cargo.toml

# Install CLI deps
cd apps/deck-cli && bun install

# Run from source (no compile step)
bun run dev -- --deck ./decks/example.toml --dry-run

# Type-check
bun run check-types
```

Path resolution is **not symmetric between the two paths**, which is worth understanding before
you debug a "database not found" error:

- **MCP server** — `resolveMcpServerPath()` checks `JOHTO_MCP_SERVER_PATH`, then
  `config.toml`, then falls back to a monorepo-relative
  `apps/mcp-server/target/release/pokemon-mcp-server`. That fallback only exists when running
  from source (it is gated on `import.meta.url` starting with `file://`, which is false inside a
  `bun build --compile` binary).
- **Card database** — `resolveDbPath()` checks `JOHTO_DB_PATH`, then `config.toml`, and then
  gives up. **There is no monorepo fallback.** When neither is set, the CLI passes no
  `DATABASE_PATH` to the child process and the Rust server applies *its own* default of
  `database/pokemon-data.sqlite3.db`, resolved relative to the server's working directory.

So `bun run dev` with no config and no env vars happens to work only when launched from the
repository root, via the Rust server's default rather than any CLI-side resolution. Running
`bun run local:setup` writes explicit paths into `config.toml` and removes the ambiguity.

## Testing the compiled binary locally

To test the exact artifact that npm publishes:

```bash
# Build the host-platform binary
bun apps/deck-cli/build/compile.ts linux-x64   # or darwin-arm64, etc.

# The binary lands here:
dist-packages/cli-platforms/linux-x64/bin/johto

# Run with env-injected paths (what the JS shim does)
JOHTO_MCP_SERVER_PATH="$(pwd)/dist-packages/mcp-server-platforms/linux-x64/bin/pokemon-mcp-server" \
JOHTO_DB_PATH="$(pwd)/dist-packages/card-data/data/pokemon-data.sqlite3.db" \
dist-packages/cli-platforms/linux-x64/bin/johto \
  --deck apps/deck-cli/decks/example.toml --dry-run
```

## Release coordination

Changes are tracked in `.changes/`. Add a pending change before opening a PR:

```bash
bun scripts/changes.ts add
```

This writes a `.changes/yyyy-mm-dd-slug.md` file. Commit it with your feature branch.

Pick the cohort by what actually ships:

| Cohort | Covers | On release |
|---|---|---|
| `cli` | the CLI and its four platform binaries | bumps all five in lockstep |
| `mcpServer` | the four MCP server platform packages | bumps all four in lockstep |
| `cardData` | `@johto-ai/card-data` | versions independently |
| `internal` | build scripts, turbo/CI config, docs, tooling | changelog only — bumps and publishes nothing |

Use `internal` for anything that ships in no package. Filing repo-only work under
`cli` bumps five published packages for a change none of them contain.

When cutting a release:

```bash
bun scripts/changes.ts release
# → bumps package.json versions, appends CHANGELOG.md, removes .changes/*.md
```

Commit the result and PR to main, then tag. The release workflow triggers on
`johto/v*.*.*` — a bare `v0.2.0` tag fires nothing:

```bash
git tag johto/v0.2.0
git push mega-blastoise johto/v0.2.0
```

Push the tag to the **publish remote**, which is `mega-blastoise`, not `origin`
— check with `git remote -v` before tagging. `@johto-ai/card-data` versions
independently on its own `johto/card-data-v*` tags.

## Adding a new subcommand

1. Create `apps/deck-cli/src/commands/my-command.ts` — export an `async function myCommand(options): Promise<void>`
2. Register it in `apps/deck-cli/src/args.ts` inside `cli()`, using a dynamic `await import()` in
   the action body so the command's dependencies stay out of cold-start for every other subcommand
3. Add docs in `apps/deck-cli/docs/`
4. Run `bun scripts/changes.ts add` to record the change

## Adding a new MCP tool

1. Implement the handler in `apps/mcp-server/src/` (Rust)
2. Rebuild: `cargo build --release --manifest-path apps/mcp-server/Cargo.toml`
3. Update `apps/deck-cli/src/agent/tools.ts` to add the tool definition to `AGENT_TOOLS`
4. `dispatchTool` (also in `tools.ts`) forwards by name, so it needs no change for a new tool —
   but if the agent should know the tool exists, add it to the `## Tool Use` list in
   `apps/deck-cli/src/agent/prompt.ts`, which is maintained by hand and drifts easily
